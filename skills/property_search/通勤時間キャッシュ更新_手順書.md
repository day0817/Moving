# 通勤時間キャッシュ更新 手順書（ローカル実行担当向け）

この手順書は、**ローカル環境（ネットワーク制限のないマシン）で動くAIエージェント**が、
`station_commute_cache.json`（駅→大手町駅の実測通勤時間キャッシュ）を作成・更新するための作業手順です。

このリモート環境（クラウド上のセッション）はネットワークポリシーにより Google Maps API・SUUMO への
アクセスがブロックされているため、この作業はローカル環境で実行する必要があります。

---

## 0. この作業の目的（背景）

`property_search.py` は、各物件の「ドアドア通勤時間」（＝駅までの徒歩時間＋大手町までの乗車時間）を
フィルタ条件（60分以下）の判定に使っています。

従来はこの乗車時間を SUUMO の検索結果バッジ（例:「50分・乗換1回」）からそのまま流用していましたが、
1つの物件に複数の候補駅（支線の駅、少し歩くが本線の駅、など）が併記されている場合、
**SUUMOのバッジがどの駅発の経路を指しているか特定できず**、徒歩時間の起点駅とズレて
実態と異なるドアドア通勤時間になることがわかりました。

（実例）大師前駅（東武大師線・支線の終着駅、徒歩4分）と西新井駅（東武伊勢崎線・本線、徒歩14分）が
併記された物件で、SUUMOバッジの「50分・乗換1回」は実際には西新井発の経路の可能性が高いのに、
徒歩4分の大師前駅の時間と機械的に合算されていた。

この問題を解消するため、**駅ごとに大手町駅までの実際の経路をGoogle Maps Directions APIで
1回だけ調べてキャッシュに保存**し、`property_search.py` 側は物件の候補駅すべてについて
「徒歩時間 + そのキャッシュ値」を計算し、最短になる駅を採用するように変更済みです
（コード変更は完了済み。あなたが行うのは**キャッシュの中身を作る作業**です）。

`property_search.py` はキャッシュを読むだけで、Google Maps APIへは一切アクセスしません。
**キャッシュを作る・更新するのは、この手順書に従って `station_commute.py` を実行したときだけです。**

## 1. 前提条件

### 1-1. Google Maps APIキーの準備

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作成（既にあれば流用可）。
2. 「Directions API」を有効化する。
3. 課金アカウントを設定する（Directions APIは従量課金制です。無料枠の範囲・料金は変動するため、
   実行前に必ず [Google Maps Platform の料金ページ](https://mapsplatform.google.com/pricing/) で
   最新の内容を確認してください）。
4. APIキーを発行する。**キーの利用制限は「Directions API」のみに絞ることを推奨**（漏洩時の被害を最小化するため）。
5. 発行したキーは **絶対にリポジトリにコミットしない**。`.env` ファイルまたは環境変数として渡します。

**【推奨】`.env` ファイルを使用する方法**:
リポジトリのルート（`Moving/`）に `.env` という名前のファイルを作成し、以下の内容を記述します。
（`.gitignore` に登録されているため、Gitにはコミットされません）

```env
GOOGLE_MAPS_API_KEY="ここに取得したAPIキー"
```

**【代替】一時的な環境変数として渡す方法**:
```bash
# 例 (bash/zsh)
export GOOGLE_MAPS_API_KEY="ここに取得したAPIキー"
```

```powershell
# 例 (PowerShell)
$env:GOOGLE_MAPS_API_KEY = "ここに取得したAPIキー"
```

### 1-2. Pythonパッケージ

`property_search.py` の実行環境に加えて、`.env` ファイルを読み込むために `python-dotenv` が必要です（インストールされていなくても動作はしますが、環境変数の手動設定が必要になります）。

```bash
pip install requests python-dotenv
```

### 1-3. 作業ディレクトリ

**必ずリポジトリのルートディレクトリ（`Moving/`）で実行してください。** 相対パスで
`properties.js` / `geocoding_cache.json` / `station_commute_cache.json` を読み書きするためです。

## 2. 実行手順

### Step 1: 最新のmainを取得する

```bash
git fetch origin main
git checkout main
git pull origin main
```

### Step 2: 対象駅の通勤時間キャッシュを更新する

**基本コマンド（推奨）**: `properties.js` に登場する全駅＋既知駅（静的辞書・geocoding_cache.json）を対象に、
**未取得の駅だけ**を新規取得します。既にキャッシュ済みの駅はAPIを呼ばずスキップされるため、
何度実行しても安全です。

```bash
python skills/property_search/station_commute.py
```

実行すると、標準エラー出力に以下のような進捗が表示されます。

```
対象駅数: 42 件
  [取得中] 大師前駅 → 大手町駅 ... 完了 (62分・乗換2回)
  [取得中] 西新井駅 → 大手町駅 ... 完了 (46分・乗換1回)
  ...
完了: 新規/再取得 8件 / スキップ(既存キャッシュ利用) 34件 / 失敗 0件
キャッシュファイル: station_commute_cache.json
```

**特定の駅だけ更新したい場合**（例: 新しく取得した物件に未知の駅が含まれる場合）:

```bash
python skills/property_search/station_commute.py --station 大師前 --station 西新井
```

**既存キャッシュも含めて全駅を再取得したい場合**（経路情報が古くなった、ダイヤ改正があった等）:

```bash
python skills/property_search/station_commute.py --force
```

### Step 3: 取得結果を確認する

```bash
git diff station_commute_cache.json
```

新規に追加された駅のエントリが、以下のような形式で入っていることを確認してください。

```json
{
  "大師前": {
    "duration_min": 62,
    "transfers": 2,
    "duration_text": "1 時間 2 分",
    "fetched_at": "2026-08-09T09:15:00"
  }
}
```

**チェックポイント**:
- `duration_min` が明らかに不自然な値（0分、数百分など）になっていないか
- `transfers` が路線構成から見て妥当か（例: 支線の駅なら本線への乗り換えが1回以上入るはず）
- 失敗件数（`失敗 N件`）が0でない場合は、標準エラー出力のログで駅名と原因（`REQUEST_DENIED`＝APIキー設定ミス、
  `ZERO_RESULTS`＝経路が見つからない、座標不明など）を確認する（トラブルシューティングは 4 章参照）

### Step 4: 物件データを通常通り更新する

キャッシュが揃ったら、通常の物件検索・データ更新を実行します（`property_search.py` は
`station_commute_cache.json` を自動的に参照します。Google Maps APIへのアクセスはこの時点では発生しません）。

```bash
python skills/property_search/property_search.py --output 物件検索結果.md
```

`物件検索結果.md` のドアドア通勤時間欄に `[実測]` / `[推定]` の表示が出るので、
実測データがどこまでカバーできているか確認してください。

### Step 5: 差分を確認してコミット・プッシュする

```bash
git add index.html style.css app.js properties.js 物件検索結果.md geocoding_cache.json station_commute_cache.json
git commit -m "Update station commute cache and properties data"
git push origin main
```

プッシュ後、数分で https://day0817.github.io/Moving/ に反映されます。

## 3. 運用ルール

- **`station_commute.py` は毎回実行しない**: 一度キャッシュされた駅は変わらない前提のため、
  新しい駅が検索結果に登場したとき、または `--force` で明示的に指示されたときだけ実行する。
- **APIコストに注意**: Directions APIは呼び出し課金です。`--force` を安易に使わず、
  基本は差分（未取得駅のみ）更新にとどめる。
- **APIキーはコミットしない**: `station_commute_cache.json` にAPIキーは含まれない設計になっているので
  そのままコミットして問題ありませんが、シェル履歴や `.env` ファイルなどにキーが残らないよう注意する。
- **到着時刻の前提**: キャッシュは「直近の平日朝9:00に大手町駅へ到着する経路」を想定して取得しています
  （`station_commute.py` の `next_weekday_9am_epoch()`）。深夜/早朝ダイヤ等、条件が異なる想定に変更したい場合は
  この関数を調整してから `--force` で再取得してください。

## 4. トラブルシューティング

| 症状 | 原因 | 対処 |
|---|---|---|
| `エラー: Google Maps APIキーが指定されていません` | 環境変数 `GOOGLE_MAPS_API_KEY` が未設定 | 1-1章の手順でAPIキーを設定 |
| ログに `REQUEST_DENIED` | APIキーが無効、Directions APIが未有効化、キーの制限設定が厳しすぎる | Google Cloud ConsoleでAPIの有効化状況・キーの制限を確認 |
| ログに `OVER_QUERY_LIMIT` | 課金設定未完了、またはクォータ超過 | 課金アカウントの設定、クォータ状況を確認 |
| ログに `ZERO_RESULTS` | 指定した到着時刻・経路で公共交通の経路が見つからない（深夜など）。**または下記4-1の既知の問題** | 駅名・座標が正しいか確認。実行時刻を変えて再試行。全駅で発生する場合は4-1を参照 |
| `[スキップ] 座標不明のため取得できません` | 駅の緯度経度が `STATIC_STATION_COORDS` にも `geocoding_cache.json` にも無い | 先に `property_search.py` を1回実行して `geocoding_cache.json` に座標を追加してから、再度 `station_commute.py` を実行 |
| `duration_min` が想定よりかなり大きい/小さい | ダイヤ改正・始発/終電間際の到着時刻設定など | `--force` で該当駅のみ再取得し、`duration_text` の内訳（Google Maps側の表記）を確認 |

### 4-1. 【既知の問題・未解決】対象駅が1件も取得できず全滅する（2026-08-09調査）

**症状**: `station_commute.py` を実行すると、対象駅（100件以上）が**すべて例外なく** `ZERO_RESULTS` で失敗する。
座標・APIキー・課金・クォータ・API有効化状況はすべて正常に見えるにもかかわらず発生する。

**調査で確認したこと（2026-08-09、実際にAPIキーを発行してテスト済み）**:
- Google Cloud Console上で Directions API・Routes API とも「有効なAPI」に表示されており、APIキーの「APIの制限」にも両方を追加済み
- 課金アカウントは「有料のアカウント」（無料トライアルではない）、クォータ使用率0%
- `mode=driving` は正常に結果が返る（同一APIキー・同一スクリプト経路で確認）
- `mode=transit` は、東京駅→新宿駅のような実在が確実な鉄道ルートでも `ZERO_RESULTS`。
  レスポンスの `available_travel_modes` に `TRANSIT` が含まれず、`DRIVING`/`WALKING`/`BICYCLING` のみが返る
- 駅名（例:「渋谷駅」「池袋駅」）を直接指定してジオコーディングさせても、`transit_station` として正しく認識されるがルートは0件
- 新しい **Routes API**（`routes.googleapis.com/directions/v2:computeRoutes`）でも同様に0件（`geocodingResults` のみで `routes` が空）
- 比較として、**海外（ニューヨーク: Times Square→Central Park）のtransitルートは同じAPIキーで正常に取得できた** → 日本国内の鉄道transitデータだけが取得できない状態
- Google Developer Forumsに完全に同一症状の未解決の投稿あり（Googleからの公式回答なし）:
  [Directions API transit mode returns ZERO_RESULTS](https://discuss.google.dev/t/directions-api-transit-mode-returns-zero-results/378267)
  この投稿でも「無料試用版→正式アカウントに切り替え済みでも解消しない」ことが報告されており、
  今回の調査結果と一致する。Google Mapsアプリ自体では同区間のtransitルートが表示されるとの報告もあり、
  API側だけがこの機能を提供できていない状態と考えられる。

**結論**: これは `.env`・APIキー設定・Google Cloud Consoleの設定ミスではなく、**Google Maps Platform側の
（少なくとも2026-08時点で）未解決の問題または日本の鉄道transitデータに関する制約**である可能性が高い。
Console側の設定を再確認しても解決しない可能性が高いため、闇雲に設定変更を繰り返さないこと。

**現在の運用方針**: この施策（Google Maps実測キャッシュによるドアドア通勤時間の精緻化）は**保留中**。
`property_search.py` は引き続き既存のSUUMOバッジ値へのフォールバックで動作させる
（`commute_source` は常に `"suumo_badge"` になる想定）。手順書冒頭で説明した「候補駅の取り違え」問題は
残るが、実害があるのは複数候補駅が併記される一部の物件のみ。

**再挑戦する場合の入り口**:
1. 上記フォーラムのスレッドや [Google Maps Platform の障害情報](https://developers.google.com/maps/incident-management?hl=ja) で解消報告がないか確認する
2. 解消していなければ、Google Cloud のサポート窓口 / [Issue Tracker](https://issuetracker.google.com/) に起票する
3. それでも解消しない場合は、Google以外の日本国内交通機関API（駅すぱあとAPI、NAVITIME APIなど）への
   切り替えを検討する（`station_commute.py` の書き直しが必要な大きめの変更になる）

## 5. このスクリプトが出力する新フィールド（参考）

`properties.js` の各物件データに以下が追加されています。

| フィールド | 内容 |
|---|---|
| `commute_source` | `"google_maps"`（実測キャッシュを使用）または `"suumo_badge"`（キャッシュ未登録駅のためSUUMOバッジ値にフォールバック） |
| `station_candidates` | 候補駅ごとの `{station, line, walk_min, commute_min, transfers, door_to_door}` の一覧（実測データがある駅のみ）。採用された最短の駅が `station`/`train_min`/`transfers`/`door_to_door` に反映されている |
