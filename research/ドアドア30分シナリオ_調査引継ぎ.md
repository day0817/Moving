# ドアドア30分シナリオ 調査引継ぎ書

**この文書の読み手は、ネットワークアクセスのあるローカル環境で作業する AI エージェントです。**
手法の設計はユーザーと合意済みです。以下の手順で実装・データ取得・検証・レポート作成を行い、
コミット（push はしない）と `USER_REVIEW.md` の作成まで進めてください。
「5. 作業を止めてユーザーに確認する条件」に当てはまった場合は、その時点で止めて報告してください。

---

## 1. 調査の問い

現行の検索条件は「郊外で広い家」を優先しています（一戸建て 80m²以上・築30年以下・ドアドア59分以下）。
ここから **面積と築年数の条件を外し、ドアドア30分以内を優先したら、どれだけ妥協が必要か** を数字で示します。
予算条件は現行と同じです。

答えとして出す数字は次の3つです。

1. ドアドア30分以内で、予算内の一戸建て（駐車場あり）が何件あるか。
2. その物件群の面積・築年数・間取りが、現行の掲載物件（ベースライン）と比べてどれだけ下がるか（中央値の差）。
3. しきい値を35分・40分に緩めると、件数と面積・築年数がどう戻るか（妥協の急所がどこにあるか）。

### 条件の対比

| 条件 | 現行（ベースライン） | 本シナリオ | 根拠・実装箇所 |
| :--- | :--- | :--- | :--- |
| 自己負担額 | 5.0万円以下 | **同じ** | `calculate_self_pay()`、`MAX_SELF_PAY`（`.agents/skills/property_search/property_search.py`） |
| SUUMO家賃上限（管理費込み） | 19.0万円 | **同じ** | `--max-rent` 既定値 |
| 住宅種別 | 一戸建て（`ts=3`） | **同じ** | `build_suumo_url()` |
| 駐車場 | あり（`tc=0400901`） | **同じ** | `build_suumo_url()` |
| 駅徒歩 | 15分以下 | **同じ** | `build_suumo_url()` の `et`、`main()` 内の `walk_min > 15` 判定 |
| 総徒歩（物件〜駅＋到着駅〜オフィス） | 18分以内 | **同じ** | `main()` 内のカットオフ |
| SUUMO乗換回数 | 1回以下（`nk=1`） | **同じ** | `build_suumo_url()` |
| 専有面積 | 80m²以上 | **撤廃** | `--min-area` |
| 築年数 | 30年以下 | **撤廃** | `main()` 内の `age_years > 30` 判定 |
| ドアドア通勤 | 59分以下 | **30分以下**（比較用に35分・40分も集計） | `main()` 内のカットオフ |
| SUUMO通勤時間フィルタ（大手町駅まで） | 50分（`tj=50`） | **40分**（`tj=40`） | `build_suumo_url()` に固定値で埋め込み |

自己負担の計算式（`calculate_self_pay()`）は、家賃＋管理費が17万円までは2割、超過分は全額、駐車場代は全額加算です。
駐車場代0円なら家賃＋管理費18.6万円が自己負担5.0万円の上限に当たります。

### 2.2 既存の通勤DBでは30分以内を判定できない

`data/station_commute.csv` に登録済みの駅（150駅）で、駅〜東京サンケイビルの所要時間（`station_to_office_min`）が

既存DBの駅だけでは30分以内の物件はほぼ出ません。
**都心寄りの駅（東西線・半蔵門線・千代田線・三田線・丸ノ内線の区部など）の通勤時間を新たに取得する必要があります。**

- SUUMO の `mb=0` が「面積下限なし」として効くか。

## 3. 手法

全体は「SUUMOで広めに候補を集める → 候補駅の通勤時間をGoogleマップで実測する → 本番と同じ式でドアドアと自己負担を計算する → しきい値ごとに集計する」の4段です。
作業ファイルはすべて `.work/d2d30/` に置きます（`.gitignore` に `.work/` を追加する）。

### 3.1 作るもの

| ファイル | 役割 | コミット |
| :--- | :--- | :---: |
| `scripts/scenario_search.py` | 条件を引数で変えられるシナリオ検索。`--stage` で段階実行する（下記） | する |
| `scripts/fetch_extra_station_commute.js` | 指定CSVの空行の駅だけ、Googleマップで通勤時間を取得する薄いラッパー | する |
| `.work/d2d30/*` | 取得データ・キャッシュ・中間結果 | しない |
| `doc/ドアドア30分シナリオ.md` | 結果レポート | する |
| `doc/README.md` | 上記レポートへの行を追加 | する |
| `.gitignore` | `.work/` を追加 | する |
| `USER_REVIEW.md` | ユーザーへのレビュー依頼（ルート直下） | しない |

コードはユーザー規約に従います: 関数型寄りで副作用を局所化、型ヒントを付ける（`Any` は使わない）、
例外は握りつぶさず意味のあるメッセージで処理、各関数の目的をコメントで明記。

### 3.2 `scripts/scenario_search.py` の段階

`importlib.util.spec_from_file_location` で `.agents/skills/property_search/property_search.py` を読み込みます。
CLI の既定値は本シナリオの値にします:
`--tj 40 --min-area 0 --max-age 999 --max-walk 15 --max-rent 19.0 --max-self-pay 5.0 --max-total-walk 18 --d2d-bands 30,35,40 --work-dir .work/d2d30`

**`--stage fetch`（SUUMO一覧の取得）**

- 5都県それぞれについて `build_suumo_url(pref_code, max_rent, min_area, max_walk)` でURLを作り、
  クエリの `tj` を `--tj` の値に差し替えます（`urllib.parse` で分解して再構成。`build_suumo_url` は `tj=50` を固定で埋め込むため）。
- ページ送りと待機（ページ間2〜4秒、都県間3〜5秒）は `main()` と同じにします。403 が返ったら即停止します。
- `parse_suumo_html` の結果を `.work/d2d30/raw_listings.json` に保存します。ファイルがあれば再取得しません（`--refresh` で再取得）。

**`--stage stations`（通勤時間を取る駅の洗い出し）**

- `main()` と同じ手順で前処理します: `rent, madori, menseki, address` のキーで重複除去し、
  `station_walk` の先頭の駅の徒歩分で `--max-walk` を判定し、`parse_age_num` で `--max-age` を判定します。
- 駐車場代0円と仮定した自己負担が `--max-self-pay` を超えるものを除きます（駐車場代を足すと必ず増えるので、ここで落としても取りこぼしは出ません）。
- 残った物件の `station_walk` に出てくる駅のうち徒歩15分以内のもので、`data/station_commute.csv` にも
  `.work/d2d30/station_commute_extra.csv` にも無い駅を、空行として `station_commute_extra.csv` に追加します。
  列構成は `data/station_commute.csv` と同じにします（後で `load_station_commute_db(csv_path)` でそのまま読むため）。

**`node scripts/fetch_extra_station_commute.js --csv .work/d2d30/station_commute_extra.csv`**

- `fetch_station_commute.js` の `run()` のうち、ループ部分だけを再現します:
  `station_to_office_min` が空の行について `fetchGoogleMapsTransit(browser, 駅名)`（月曜8:45着、到着地は東京サンケイビル）を呼び、
  失敗したら `fetchTransitHtml` ＋ `parseRoute01`（Yahoo!路線情報）にフォールバックします。
  ブラウザ起動オプション、待機（2.5秒）、行への書き戻し項目は `run()` と同じにします。
- 1駅取得するごとに `saveCsv` で**指定したCSVだけ**に保存します。`buildStationCommuteJs()` は呼びません。
- 取得できなかった駅は `memo` 列に `取得失敗` と書き、件数を最後に出力します。

**`--stage parking`（駐車場代の取得）**

- `data/station_commute.csv` と `station_commute_extra.csv` を `load_station_commute_db` で読み、辞書をマージします（同名駅は本番側を優先）。
- `evaluate_best_commute` でドアドアを計算し、`--d2d-bands` の最大値以下かつ総徒歩 `--max-total-walk` 以下の物件だけを対象に、
  駐車場代が未取得の物件の詳細ページを取得して `parse_parking_info` で解析します。
- キャッシュは `load_parking_cache()`（本番、読み取りのみ）と `.work/d2d30/parking_cache_extra.json`（書き込み先）の2段にします。
  詳細ページ取得の待機（2.5〜4秒）と掲載終了判定は `main()` と同じにします。

**`--stage report`（集計）**

- 自己負担 `calculate_self_pay(rent, admin, parking_fee)` が `--max-self-pay` 以下、ドアドアが帯の最大値以下、総徒歩が上限以下の物件を確定します。
- `main()` と同じ同一物件統合（自己負担の小数1桁・面積・築年数/階建て・住所の丁目レベルが一致したら統合）を行います。
  `main()` の中の入れ子関数なので import できません。ロジックを写してください。
- 出力:
  - `.work/d2d30/candidates.json`: 確定物件の全項目（`properties.js` の要素と同じキー＋`bedrooms`、`is_estimated`）。
  - `.work/d2d30/tables.md`: 4章のレポートに貼る表（下記の集計表と物件一覧）。
- `evaluate_best_commute` は、DBに無い駅について SUUMO の値から推定したルートを返します（戻り値の `is_db` が False）。
  採用ルートが推定のものは `is_estimated: true` とし、件数には含めず別枠で列挙します。

### 3.3 集計する指標

帯は累積（ドアドア30分以下 / 35分以下 / 40分以下）とし、ベースライン列を並べます。

| 指標 | 定義 |
| :--- | :--- |
| 件数 | 同一物件統合後の件数 |
| 専有面積 | 最小 / 中央値 / 最大（m²） |
| 築年数 | 最小 / 中央値 / 最大（年、新築=0） |
| 居室3以上の割合 | 間取り表記の先頭の数字が3以上の物件の割合（`2SLDK` は2として数える） |
| 現行条件も満たす件数 | 80m²以上かつ築30年以下の件数（妥協なしで30分以内が取れるかの確認） |
| 3階建ての割合 | `age_floor` に `3階建` を含む割合（狭小住宅の目安） |
| 自己負担 | 中央値（万円） |
| 駅徒歩 | 中央値（分） |
| 駐車場 | 敷地内（`parking_dist == 0`）と近隣の件数、駐車場代の記載が無い件数 |

「妥協の量」は、30分以下の帯とベースラインの中央値の差（面積 −○m²、築年数 +○年、居室3以上の割合 −○ポイント）で表します。

## 4. 手順

### Step 0: SUUMOパラメータの確認

1. `tj=30`、`tj=40`、`tj=50` で東京都の1ページ目を取得し、`parse_max_pages` と件数表示から件数が `30 < 40 < 50` の順に増えることを確認します。
   件数が同じなら `tj` の値が無視されている可能性があるので止めて報告します。
2. `mb=0` と `mb=80` を比べ、`mb=0` の方が件数が多いことを確認します。
3. 確認結果（各件数）はレポートの「手法と制約」に記録します。

### Step 1: 実装と、本番ロジックとの一致確認（オフライン）

`scripts/scenario_search.py` に `--stage selfcheck` を用意し、ネットワークを使わずに次を確認します。

- `properties.js` の36件それぞれについて、`calculate_self_pay(rent, admin, parking_fee)` が保存済みの `self_pay` と一致すること。
- 本番DB（`data/station_commute.csv`）だけで `evaluate_best_commute` を計算し、`door_to_door` と `total_walk_min` が保存済みの値と一致すること。

`evaluate_best_commute` に渡す辞書は `station`、`line`、`station_walk`、`walk_min`、`train_min`、`transfers` を
`properties.js` の値から組み立てます。設計時にこの方法で36件すべて一致することを確認済みです。
1件でも不一致なら、配線（引数の組み立て方）の誤りなので直してから進みます。
なお本番の `main()` は `train_min` に SUUMO の大手町駅までの時間（`commute_min`）を渡しています。
この値は DB に無い駅の推定ルートでだけ使われます。本番取得（`--stage stations` 以降）では `main()` と同じく `commute_min` を渡してください。

### Step 2: 取得と集計

PowerShell の例:

```powershell
$env:PYTHONIOENCODING="utf-8"
py scripts/scenario_search.py --stage fetch
py scripts/scenario_search.py --stage stations
node scripts/fetch_extra_station_commute.js --csv .work/d2d30/station_commute_extra.csv
py scripts/scenario_search.py --stage parking
py scripts/scenario_search.py --stage report
```

金曜20:30前後（週次バッチの実行時間帯）は避けてください。SUUMO へのアクセスが重なります。

### Step 3: 結果の検証

- **Googleマップ取得値の妥当性**: `station_commute_extra.csv` の各駅について、`station_to_office_min` が SUUMO の大手町駅までの時間
  （`raw_listings.json` の `commute_min`）より短い、または15分以上長い駅を一覧にします。
  同名の別駅を拾った可能性があるので、該当駅は Googleマップで経路を目視確認し、誤りなら `STATION_QUERY_OVERRIDES` と同じ考え方で
  「駅名(都県名)」に直して再取得します（本番スクリプトは変更せず、ラッパー側に上書き表を持つ）。
- **抜き取り確認**: 30分以下の帯から3件を選び、SUUMO の詳細ページで家賃・管理費・駅徒歩・駐車場の記載が `candidates.json` と一致することを確認します。
- **帯の単調性**: 件数が 30分以下 ≤ 35分以下 ≤ 40分以下 になっていることを確認します。

### Step 4: レポート作成

`doc/ドアドア30分シナリオ.md` を次の構成で書きます。結論を先頭に置きます。

1. **結論**: 30分以下の件数と、ベースラインとの中央値の差（面積・築年数・居室数）。35分・40分で何が戻るかを1〜2文で。
2. **帯別の集計表**: 3.3 の指標 × {30分以下, 35分以下, 40分以下, ベースライン}。
3. **30分以下の物件一覧**: 駅、路線、物件名、家賃/管理費、自己負担、ドアドア（内訳）、間取り/面積、築年数、駐車場、リンク。
   列は `doc/物件検索結果.md` の表に合わせ、駐車場の列を足します。
4. **駅別の件数**: 30分以下・40分以下の帯で、どの駅・路線に物件があるか。
5. **手法と制約**: 取得日、条件、Step 0 の件数、推定ルートで件数外とした物件、下記の制約。

レポートに必ず書く制約:

- 通勤時間は Googleマップの「月曜8:45着」の第1候補1本です。座れるかどうか、混雑は評価していません。
- 駐車場代は詳細ページの記載から読んでいます。記載が無い物件は0円として計算しているため、自己負担は下振れしている可能性があります（件数を明記）。
- 学区・住環境は評価していません（`doc/背景.md` の教育要件は未検証）。
- SUUMO の掲載は取得日時点のスナップショットです。

書式は `doc/` の既存文書に合わせ、`technical-writing` スキルの規則（結論先行、出典のない断定をしない、ダッシュ記号を使わない）に従います。
`doc/README.md` の「目的別の読み方」の表にレポートの行を追加します。

### Step 5: コミットとレビュー依頼

- 3.1 の「コミット: する」のファイルをコミットします。push はしません（ユーザーがローカルのIDEで確認してから push します）。
  メッセージは Conventional Commits、本文は日本語です。例: `feat(analysis): ドアドア30分シナリオの検索スクリプトと調査レポートを追加`
- リポジトリ直下に `USER_REVIEW.md` を作ります。必須項目は「確認依頼の目的」「主要な観点」「重点的にレビューしてほしい箇所」です。
  重点箇所には少なくとも次を含めます: Step 3 で目視確認した駅とその判断、推定ルートで件数外にした物件、駐車場代が不明の物件。

## 5. 作業を止めてユーザーに確認する条件

- SUUMO が 403 を返した、または Step 0 で `tj`・`mb` が効いていないと判断した。
- Step 1 の一致確認で不一致が解消できない。
- Googleマップ・Yahoo!の両方で取得できなかった駅が、対象駅の2割を超えた。
- 40分以下の帯でも0件だった（取得か計算の誤りを疑う）。
- 本番ファイル（2.3 の一覧、`data/parking_cache.json`）に差分が出た。`git status` で毎段確認してください。
